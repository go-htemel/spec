# Spec

`github.com/go-htemel/spec` provides the spec types used by the htemel generators, and the spec
documents that describe HTML, SVG and MathML elements and attributes.

- `spec.go` defines the types: `Spec`, `Element`, and the `Attribute` interface with one
  implementation per attribute type (String, Char, Number, Float, Bool, Enum, SST, PrefixedCustom).
- `specs/html.json`, `specs/svg.json` and `specs/mathml.json` are the spec documents, one per
  language. They are generated by `cmd/specgen2` (see below).

The primary consumer is [`github.com/go-htemel/htemel`](https://github.com/go-htemel/htemel), which
reads these types and documents.

## Install

```text
go get github.com/go-htemel/spec
```

## Regenerating the specs

`cmd/specgen2` builds the documents offline from committed, versioned inputs under `data/`:

- `data/webref/` (elements and Web IDL from `@webref/elements` and `@webref/idl`)
- `data/bcd/` (the html, svg and mathml parts of `@mdn/browser-compat-data`)
- `data/whatwg/indices.html` (the WHATWG HTML element and attribute index tables, from a commit
  snapshot)
- `data/overlay/{html,svg,mathml}.json` (hand-maintained judgment calls)
- `data/SOURCES.json` (versions, integrity hashes and retrieval dates of the vendored inputs)

The workflow, in order:

```text
# 1. Refresh npm inputs. Reads local tarballs; create them first with npm pack (needs network).
npm pack @webref/elements@2.9.2 @webref/idl@3.86.0 @mdn/browser-compat-data@8.1.7
go run ./cmd/specgen2 vendor -elements elements.tgz -idl idl.tgz -bcd bcd.tgz

# 2. Re-pin the WHATWG index (needs network). Without -sha, pins the currently deployed commit.
go run ./cmd/specgen2 fetch [-sha <whatwg/html commit>]

# 3. Build candidates (offline). Writes specs/candidates/{html,svg,mathml}.json and *.provenance.json.
go run ./cmd/specgen2 generate

# 4. Write docs/webref-coverage.md (candidates compared with the committed specs).
go run ./cmd/specgen2 report

# 5. Review the differences, then promote the three documents. Provenance files stay in candidates/.
go run ./cmd/specgen2 diff -old specs/html.json -new specs/candidates/html.json
cp specs/candidates/{html,svg,mathml}.json specs/
```

Steps 1 and 2 are the only ones that touch the network, and they are only needed when the inputs
change. `generate` and `report` need only the committed files, and the output is deterministic for
the same inputs, so CI can run `generate` offline and fail if `specs/candidates/` differs from what
is committed. Note that `generate` also reads the existing `specs/*.json` for element and attribute
descriptions (`-legacy`, default `specs`), so promote candidates before regenerating.

`docs/webref-coverage.md` is written by `report`, except for the hand-written analysis block between
the `notes:begin` and `notes:end` markers, which is preserved across runs.

### Overlay files

`data/overlay/<spec>.json` records the judgment calls that the vendored sources do not make. Each
attribute override is an entry under `attributes` (keyed by element, or `@global`) with a `type` and a
`reason`. The code rejects an override without a reason, so the file doubles as the record of why
each decision was made. The other keys are lists (for example `void`, `no_text`, `raw_text`, `text`,
`ignore_bcd`) or maps (`idl_renames`); the `comment` key at the top of each file explains them.
`content_model` (keyed by tag; `kind`, `categories`, `elements`, `text`, `note`, `reason`) replaces the
model derived from the index's Children column, for cells with no mechanical mapping (noscript's
"varies") or where the index's model would mislead generators (template).

## Legacy generator: `cmd/specgen`

`cmd/specgen` is legacy and deprecated. It scrapes element names from the live WHATWG page and takes
attributes from hand-written Go in `html_spec.go`. It is kept for history only and must not be used
to produce new data: with its defaults it overwrites `specs/`. Use `cmd/specgen2` instead.

## Schema

A spec document is a JSON object:

```json
{
  "name": "html",
  "elements": [ { "tag": "a", "attributes": [ ... ] } ],
  "attributes": [ ... ]
}
```

- `name`: the spec name.
- `elements`: the elements of the spec. `attributes` at the top level are global attributes that apply
  to every element.

Element fields:

| field | type | notes |
|---|---|---|
| `tag` | string | element name |
| `description` | string | optional |
| `attributes` | array | optional; attribute objects as below |
| `void` | bool | optional; element has no children |
| `text` | bool | optional |
| `raw_text` | bool | optional; text is raw (script, style): it is not entity-decoded, so it must not be HTML-escaped when rendered |
| `deprecated` | bool | optional; obsolete or deprecated in the source specification |
| `interface` | string | optional; DOM interface, e.g. `HTMLAnchorElement` |
| `categories` | array of strings | optional; content categories such as `flow`, `phrasing`, `interactive`; sorted; vocabulary below |
| `content_model` | object | optional; the children the element accepts (HTML only, from the WHATWG index); see below |

`content_model` fields:

| field | type | notes |
|---|---|---|
| `kind` | string | `empty` (no children; not the same as `void`: iframe and selectedcontent are empty but take an end tag), `text` (text only), `transparent` (the parent's content model, plus `elements`), `children` (the union of `categories`, `elements` and `text`), `unknown` (not expressible; treat as unchecked: template) |
| `categories` | array of strings | optional; permitted child categories, sorted; a child is permitted if it has any of them |
| `elements` | array of strings | optional; explicitly permitted child tags, sorted (`["li"]` for ul) |
| `text` | bool | optional; text nodes permitted (inter-element whitespace always is) |
| `note` | string | optional; the index's Children prose (a `*` means the element definition adds conditions) and any mapping note |

Ordering and conditional rules ("one summary element followed by flow content", "if the element has a
src attribute ...") are not expressed: models list the union of everything permitted, so checks built
from them can miss invalid markup but never reject valid markup.

Category vocabulary (`spec.ContentCategories`): `metadata`, `flow`, `sectioning`, `heading`,
`phrasing`, `embedded`, `interactive`, `palpable`, `script-supporting`, `form-associated`, `listed`,
`labelable`, `submittable`, `resettable`, `autocapitalize-inheriting`, `sectioning-root`.

Attribute fields. Every attribute has `name` and `attribute_type`; the rest are optional.

| field | type | notes |
|---|---|---|
| `name` | string | attribute name |
| `description` | string | optional |
| `attribute_type` | string | one of `AttributeTypeString`, `AttributeTypeChar`, `AttributeTypeNumber`, `AttributeTypeFloat`, `AttributeTypeBool`, `AttributeTypeEnum`, `AttributeTypeSST`, `AttributeTypePrefixedCustom` |
| `deprecated` | bool | optional |
| `url` | bool | optional; only on `AttributeTypeString`; the value is a URL |
| `allowed` | object | `AttributeTypeEnum` only; set of allowed values, keys sorted |
| `allow_empty` | bool | `AttributeTypeEnum` only |
| `allow_custom` | bool | `AttributeTypeEnum` only; values beyond `allowed` are permitted |

Consumers should ignore unknown keys. The `raw_text`, `deprecated`, `interface`, `categories`, `content_model` and `url`
fields are omitted when empty, so documents that do not use them are unchanged.
